1문제 해결

로컬 주소가 안 열리는 경우는 대부분 서버가 꺼져 있거나, 다른 프로그램이 그 포트를 쓰고 있는 경우다. 증상을 찾아 확인 명령을 돌리고 해결을 따른다. 기본 포트는 open_dashboard.sh의 8765다.

증상 원인 확인 해결
브라우저가 "연결할 수 없음", curl이 Connection refused 그 포트를 듣는 서버가 없다. 재부팅하면 서버가 사라진다(3절) ss -ltn | grep 8765가 아무것도 찍지 않는다 source .venv/bin/activate 뒤 ./scripts/open_dashboard.sh
서버를 띄울 때 Address already in use 다른 프로그램이 그 포트를 쓰고 있다. 한 포트에는 하나만 앉는다(4절) ss -ltnp | grep :8765로 어느 프로그램인지 본다 다른 포트로 띄운다. PORT=8766 ./scripts/open_dashboard.sh
열리긴 하는데 다른 프로젝트 페이지나 404가 뜬다 다른 프로젝트의 서버가 그 포트를 잡고 있다. open_dashboard.sh는 포트에 연결만 되면 새로 띄우지 않는다 ss -ltnp | grep :8765, curl -sI http://127.0.0.1:8765/ | grep -i server 그 서버를 끄거나 PORT=로 다른 포트를 쓴다
/dashboard.html만 404 대시보드를 아직 만들지 않았다. docs/dashboard.html은 생성물이라 저장소에 없다(페이지가 만들어지는 방식 2절) ls docs/dashboard.html .venv를 켜고 python3 automation/render_dashboard.py
ModuleNotFoundError: No module named 'markdown' 시스템 파이썬으로 돌았다. .venv를 켜지 않았다(12절) which python3가 /usr/bin/python3를 찍는다 source .venv/bin/activate
Playground가 빈 화면, 개발자 도구에 CORS 오류 file://로 열었다. ES 모듈이 막힌다(11절) 주소창이 file://로 시작한다 http://127.0.0.1:8765/playground/로 연다
몇 초 기다리다 timed out 방화벽이 요청을 버리거나 주소가 틀렸다. 서버가 없을 때와 다르다(5절) curl -m 5 -v <주소> 주소, 포트, 네트워크 연결을 확인한다
공개 사이트를 갱신했는데 옛 내용이 보인다 브라우저와 CDN이 10분 동안 사본을 쓴다(max-age=600). 또는 동기화가 아직 안 끝났다(9절) curl -sI <주소> | grep -i last-modified Ctrl+Shift+R로 다시 받는다. 그래도 옛 것이면 Actions 탭의 publish-site 실행을 본다
GitHub API가 403, rate limit exceeded 로그인 없는 요청은 공인 주소 하나당 시간당 60회다(10절) curl -s https://api.github.com/rate_limit gh auth login 뒤 gh api로 요청한다(시간당 5000회)
재부팅할 때마다 서버를 다시 띄우기 귀찮다 nohup은 재부팅을 견디지 못한다 uptime -s로 마지막 부팅 시각을 본다 systemd 사용자 서비스로 등록한다(12절)

2한눈에 보기

로컬 서버든 외부 서버든 HTTP 대화 자체는 같다. 외부 서버에는 그 앞뒤로 단계가 붙는다. 이름을 주소로 바꾸고(DNS), 공유기와 통신사 망을 지나고(라우팅), 통로를 암호화한다(TLS).

① 주소창에 URL을 넣는다
② (외부만)  DNS   이름을 IP 주소로 바꾼다
③           TCP   그 주소의 포트와 통로를 연다         ← 서버가 없으면 여기서 Connection refused
④ (https만) TLS   인증서를 확인하고 통로를 암호화한다
⑤           HTTP  "GET /dashboard.html"을 보내고 "200 OK"와 내용을 받는다
⑥ 브라우저가 HTML을 그리고, 필요한 JS·CSS·그림을 ③–⑤로 더 받는다

URL 읽는 법

http://127.0.0.1:8765/dashboard.html
└┬─┘   └───┬───┘ └┬─┘└──────┬──────┘
 │         │      │         └─ 경로: 어떤 파일을 달라는지 (docs/dashboard.html)
 │         │      └─ 포트: 그 컴퓨터의 어느 프로그램인지
 │         └─ 주소: 어느 컴퓨터인지 (127.0.0.1은 이 PC 자신)
 └─ 방식: HTTP로 대화하겠다 (https면 암호화한 HTTP)

3프로세스와 서버

서버는 메모리에서 도는 프로세스라서, 재부팅하면 사라진다. 부팅할 때 다시 띄우려면 따로 등록해야 한다.

  • 프로그램은 디스크에 저장된 파일이다. 아직 일하지 않는 업무 설명서와 같다.
  • 프로세스는 그 프로그램이 실행되어 메모리에서 돌고 있는 상태다. 직원이 설명서를 들고 창구에 앉아 있는 것과 같다.
  • 메모리는 전원이 꺼지면 지워진다. 그래서 재부팅하면 모든 프로세스가 끝난다. 부팅 때 다시 띄우는 일은 systemd나 cron의 @reboot가 한다(12절).
  • 클라이언트는 요청하는 프로그램이다. 브라우저, curl, gh, git, pip가 여기 속한다.
  • 서버는 요청을 기다렸다가 응답하는 프로그램이다. 로컬의 http.server, 인터넷의 GitHub Pages가 여기 속한다.
  • 클라이언트와 서버가 꼭 다른 컴퓨터에 있을 필요는 없다. 로컬 대시보드는 둘 다 같은 PC 안에 있다.
uptime -s                                          # 마지막으로 부팅한 시각
ps -eo pid,lstart,args | grep [h]ttp.server         # 돌고 있는 http.server와 시작 시각

grep [h]ttp.server처럼 첫 글자를 대괄호로 감싸면 grep 자기 자신이 결과에 섞이지 않는다.

4주소와 포트

IP 주소는 어느 컴퓨터인지를, 포트는 그 컴퓨터의 어느 프로그램인지를 정한다.

IP 주소

  • 네트워크에서 컴퓨터를 찾는 숫자다. IPv4는 185.199.108.153처럼 0–255 숫자 네 묶음이다.
  • 127.0.0.1은 "이 컴퓨터 자신"을 뜻한다. 루프백(loopback)이라 하고 localhost라는 이름도 같은 곳이다. 이 주소로 보낸 요청은 PC 밖으로 나가지 않는다. 인터넷이 끊겨도 동작하고, 다른 PC에서는 접속할 수 없다.
  • 사설 주소는 집이나 사무실 안에서만 쓰는 주소다. 192.168.x.x, 10.x.x.x, 172.16.x.x–172.31.x.x가 여기 속한다. 인터넷에서는 이 주소로 찾아갈 수 없다(9절).

포트와 listen

  • 한 컴퓨터에서 여러 프로그램이 동시에 통신한다. 그래서 주소만으로는 어느 프로그램에 갈지 모른다. 포트는 그것을 정하는 0–65535 사이의 번호다.
  • 서버 프로그램은 운영체제에 "이 번호로 오는 연결은 내가 받겠다"고 등록하고 기다린다. 이것을 listen이라 한다.
  • 한 주소와 포트 쌍에는 프로그램 하나만 listen할 수 있다. 이미 쓰는 번호에 띄우면 Address already in use로 실패한다.
포트 쓰는 곳
22 SSH(원격 접속)
53 DNS
80 HTTP. 주소에 포트를 안 쓰면 http는 80으로 간다
443 HTTPS. 주소에 포트를 안 쓰면 https는 443으로 간다
8765 scripts/open_dashboard.sh의 기본값. 계속 띄워 둔다
8799 scripts/check_playground.sh. 검사가 끝나면 끈다
8798 scripts/check_site.sh가 공개 사본을 띄우는 번호

bind: 누구의 연결을 받을까

묶는 주소 누가 접속할 수 있나
--bind 127.0.0.1 이 PC 자신만. travplan 스크립트는 모두 이것을 쓴다
--bind 0.0.0.0 같은 공유기에 붙은 사람 누구나(http://192.168.x.20:8765처럼)

docs/에는 아직 공개하지 않은 내용도 있다. 그래서 이 PC에서만 보이게 묶는다.

5TCP 연결

TCP는 두 프로그램 사이에 믿을 수 있는 통로를 만든다. 데이터가 빠지거나 순서가 뒤바뀌지 않게 보장하고, 사라진 조각은 다시 보낸다. HTTP는 이 통로 위에서 오간다.

단계 패킷 전화 비유
1. 연결 요청 SYN 전화를 건다
2. 수락 SYN-ACK 상대가 받는다
3. 확인 ACK "여보세요"가 오가고 통화가 시작된다
4. 데이터 HTTP 요청과 응답 용건을 말하고 답을 듣는다
5. 끊기 FIN 전화를 끊는다

거절과 시간 초과는 다르다

연결이 실패한 모양을 보면 원인을 좁힐 수 있다.

모양 무슨 일 뜻
Connection refused, 즉시(0 ms) 운영체제가 거절 신호(RST)를 곧바로 돌려보냈다 컴퓨터는 있는데 그 포트에 서버가 없다
timed out, 몇 초 뒤 요청에 아무 답이 없었다 방화벽이 버렸거나, 그 주소에 컴퓨터가 없다
Could not resolve host DNS가 이름을 주소로 바꾸지 못했다 이름이 틀렸거나 DNS에 닿지 못한다 
nc -zv 127.0.0.1 8765      # z: 연결만 해 보고 끊는다, v: 결과를 말로 찍는다

Connection to 127.0.0.1 8765 port [tcp/*] succeeded!                  ← 서버가 있다
nc: connect to 127.0.0.1 port 8799 (tcp) failed: Connection refused    ← 서버가 없다

6HTTP

HTTP는 TCP 통로 안에서 쓰는 글자 대화다. 요청과 응답 모두 첫 줄, 헤더, 빈 줄, 본문의 네 부분이다. 브라우저는 이 글자를 자동으로 쓰고 읽을 뿐이다.

손으로 써 보는 HTTP

nc는 TCP 통로만 열고 아무것도 해석하지 않는다. 요청을 손으로 써서 보내도 서버가 답한다.

printf 'GET /playground/ HTTP/1.0\r\nHost: 127.0.0.1\r\n\r\n' | nc -q 2 127.0.0.1 8765 | head -12

보낸 것
GET /playground/ HTTP/1.0             ← 요청 줄: 메서드, 경로, 버전
Host: 127.0.0.1                       ← 헤더(이름: 값)
                                      ← 빈 줄: 헤더 끝
받은 것
HTTP/1.0 200 OK                       ← 상태 줄: 버전, 상태 코드, 설명
Server: SimpleHTTP/0.6 Python/3.10.12
Content-type: text/html
Content-Length: 31813                 ← 본문 크기(바이트)
Last-Modified: Tue, 06 Oct 2026 06:08:23 GMT
                                      ← 빈 줄
<meta charset="utf-8">                ← 본문: Playground의 HTML 그대로
<title>travplan Playground</title>

줄 끝의 \r\n은 HTTP가 정한 줄바꿈이다. 헤더 뒤의 빈 줄 하나가 "헤더는 여기까지"라는 표시다.

메서드: 무엇을 해 달라는가

메서드 뜻 예
GET 달라 페이지 열기, 파일 받기
HEAD 머리말만 달라 파일이 있는지, 언제 바뀌었는지만 확인(curl -I)
POST 받아서 처리해 달라 로그인, 글 올리기, PR 만들기
PUT, PATCH 이것으로 바꿔 달라 설정 저장, PR 본문 고치기
DELETE 지워 달라 글 삭제

로컬 http.server는 GET과 HEAD에 200, POST와 DELETE에 501을 낸다. 파일을 내주기만 하는 서버라서 무언가를 받아 처리하는 기능이 없기 때문이다.

상태 코드: 첫 자리 숫자가 종류다

코드 뜻 언제
200 OK 성공 파일을 찾아 보냈다 로컬·외부에서 봄
301 Moved Permanently 이사 갔다. Location으로 가라 폴더 주소 끝에 /가 없을 때, http로 왔을 때 봄
304 Not Modified 바뀐 것 없다. 가진 것을 써라 캐시 확인 요청 봄
400 Bad Request 요청 모양이 틀렸다 HTTP 형식을 어긴 요청
401 Unauthorized 누구인지 밝혀라 로그인이나 토큰이 없다
403 Forbidden 알지만 거절한다 권한이 없거나 요청 한도를 넘었다 봄
404 Not Found 그런 것 없다 경로가 틀렸거나 파일이 없다 봄
500 Internal Server Error 서버 안에서 오류가 났다 서버 프로그램의 버그
501 Not Implemented 그 기능은 없다 http.server에 POST를 보냈다 봄
502, 503 뒤의 서버가 답하지 않는다, 지금 바쁘다 중계 서버 뒤의 원본이 죽었거나 과부하다

정리하면 2xx는 성공, 3xx는 다른 곳으로 가라, 4xx는 요청한 쪽 잘못, 5xx는 서버 쪽 잘못이다.

헤더: 요청과 응답에 붙는 꼬리표

헤더 방향 뜻
Host 요청 어느 사이트에 묻는지. 서버 한 대가 사이트 여럿을 맡을 때 이것으로 가른다
User-Agent 요청 요청한 프로그램 이름(curl/7.81.0, 브라우저 이름)
Accept 요청 받고 싶은 형식
Authorization 요청 누구인지 밝히는 토큰(10절)
If-Modified-Since, If-None-Match 요청 "이 시각, 이 판 이후로 바뀌었으면 달라"
Content-Type 응답 본문 형식(text/html, application/json)
Content-Length 응답 본문 크기(바이트)
Last-Modified, ETag 응답 마지막 수정 시각, 판 번호. 캐시 확인에 쓴다
Cache-Control 응답 얼마 동안 다시 묻지 말고 써도 되는지(max-age=600은 10분)
Location 응답 3xx일 때 갈 곳
Set-Cookie, Cookie 응답, 요청 서버가 맡긴 꼬리표를 다음 요청마다 돌려준다(로그인 유지)

리다이렉트: 여기가 아니라 저기로 가라

  • /playground(끝에 / 없음)를 달라고 하면 301과 Location: /playground/가 온다. 폴더 주소는 끝에 /가 있어야 그 안의 파일을 상대 경로로 찾기 때문이다.
  • 공개 사이트에 http://로 가면 301과 함께 https:// 주소로 돌려보낸다. 암호화하지 않은 연결로는 페이지를 주지 않는다.
  • 브라우저는 Location을 보고 자동으로 다시 요청한다. curl은 -L을 줘야 따라간다.

캐시: 이미 가진 것은 다시 받지 않는다

  • 서버는 응답에 Last-Modified를 붙인다. 다음 요청에 If-Modified-Since: 그 시각을 붙이면, 바뀌지 않았을 경우 본문 없이 304만 온다.
  • 4.7 MB짜리 대시보드에 이렇게 다시 물었더니 받은 양이 0 바이트였다.
  • 공개 사이트는 cache-control: max-age=600을 보낸다. 10분 동안은 묻지도 말고 가진 것을 쓰라는 뜻이다. 그래서 갱신 직후에 옛 페이지가 보일 수 있다. Ctrl+Shift+R은 이 사본을 무시하고 다시 받는다.
LM=$(curl -sI http://127.0.0.1:8765/dashboard.html | grep -i '^last-modified' | cut -d' ' -f2- | tr -d '\r')
curl -s -o /dev/null -w '%{http_code}, %{size_download} bytes\n' -H "If-Modified-Since: $LM" http://127.0.0.1:8765/dashboard.html

304, 0 bytes

HTTP 버전

버전 특징 본 곳
HTTP/1.0 요청 하나마다 연결을 새로 열고 닫는다 로컬 http.server
HTTP/1.1 연결 하나를 여러 요청에 이어 쓴다 공개 사이트의 http 리다이렉트

HTTP는 기억하지 않는다

서버는 요청마다 처음 보는 손님처럼 대한다. 이것을 stateless라 한다. 그래서 로그인처럼 "누구인지"가 필요하면 요청마다 쿠키나 토큰을 헤더에 붙인다. HTTPS는 같은 HTTP 대화를 TLS로 암호화한 통로 안에서 하는 것이다(9절).

8curl

curl은 화면을 그리지 않는 브라우저다. 요청을 보내고 받은 내용을 그대로 보여 준다. 그래서 무엇이 오가는지 들여다볼 때 쓴다. git, pip, gh도 속으로는 같은 HTTP 요청을 보낸다.

자주 쓰는 옵션

옵션 하는 일
-v 연결, 암호화, 요청, 응답 과정을 모두 보여 준다. >는 보낸 줄, <는 받은 줄, *는 curl의 설명이다
-I HEAD 요청. 본문 없이 헤더만 받는다
-i 본문 앞에 응답 헤더도 찍는다
-L 3xx 리다이렉트를 따라간다
-o 파일, -O 본문을 그 파일에 저장한다, 주소의 파일 이름으로 저장한다
-s, -S 진행 표시를 끈다, 그래도 오류는 찍는다(-sS로 같이 쓴다)
-f 4xx·5xx면 본문을 찍지 않고 실패(종료 코드 22)로 끝낸다. 스크립트에서 쓴다
-X 메서드 메서드를 바꾼다(-X POST)
-d 데이터 요청 본문에 데이터를 싣는다. 메서드는 저절로 POST가 된다
-H '이름: 값' 요청 헤더를 더한다
-m 초 그 시간이 지나면 포기한다
-w '형식' 끝난 뒤 상태 코드, 시간 같은 값을 찍는다(아래 표)

> GET /dashboard.html HTTP/1.1                         ← 보낸 요청
> Host: 127.0.0.1:8765
> User-Agent: curl/7.81.0
> Accept: */*
>
< HTTP/1.0 200 OK                                      ← 받은 응답
< Server: SimpleHTTP/0.6 Python/3.10.12
< Content-type: text/html
< Content-Length: 4734038

-w로 단계별 시간 재기

curl -s -o /dev/null -w 'DNS %{time_namelookup}  TCP %{time_connect}  TLS %{time_appconnect}  첫바이트 %{time_starttransfer}  끝 %{time_total}  HTTP/%{http_version} %{http_code}  %{remote_ip}:%{remote_port}\n' https://geonhee-lee.github.io/travplan-site/
변수 뜻
time_namelookup DNS가 끝난 시각(시작부터 잰 초)

time_appconnect TLS가 끝난 시각(http면 0)

시각은 모두 시작부터 누적한 값이다. 한 단계가 걸린 시간은 앞 단계 값을 빼서 구한다(9절의 표).

9외부 서버까지

외부 서버로 가는 요청은 DNS, 공유기, 통신사 망, TLS를 차례로 거친다. 받는 쪽도 서버 한 대가 아니라 전 세계에 흩어진 사본(CDN)이다. 공개 사이트에 요청 하나를 보내고 단계별 시간을 쟀다.

단계 로컬(127.0.0.1) 외부(github.io) 하는 일
DNS 0.00002초 0.020초 이름을 IP 주소로 바꾼다
TCP 연결 0.0001초 +0.003초 상대 포트와 통로를 연다
TLS 없음 +0.027초 상대 신원을 확인하고 통로를 암호화한다
첫 바이트 0.001초 +0.228초 서버가 답을 준비해 보내기 시작한다
합계 0.001초 0.279초

DNS: 이름을 주소로

컴퓨터는 숫자 주소로만 통신한다. 그래서 geonhee-lee.github.io라는 이름을 먼저 주소로 바꿔야 한다.

dig +noall +answer geonhee-lee.github.io

geonhee-lee.github.io.  1351  IN  A  185.199.108.153
geonhee-lee.github.io.  1351  IN  A  185.199.109.153
geonhee-lee.github.io.  1351  IN  A  185.199.110.153
geonhee-lee.github.io.  1351  IN  A  185.199.111.153
└ 이름               └ TTL(초) └ A: IPv4 주소
  • PC는 통신사가 정해 준 DNS 서버에 묻는다(resolvectl status로 확인). 그 서버는 모르면 최상위 서버, .io 담당, github.io 담당에 차례로 물어 답을 찾는다.
  • TTL은 그 답을 기억해 둘 시간이다. 그동안은 다시 묻지 않으므로 다음 요청이 빨라진다.
  • 주소가 넷인 것은 서버를 여러 대 두었기 때문이다. 하나가 죽어도 나머지로 접속한다.
  • localhost는 DNS에 묻지 않는다. /etc/hosts 파일에 127.0.0.1로 적혀 있다.

사설 주소, 공유기, NAT

ip route show default      # 바깥으로 나가는 기본 경로
ip -4 -o addr show         # 이 PC의 주소들

default via 192.168.x.1 dev eth0  proto dhcp metric 100    ← 유선
default via 192.168.x.1 dev wlan0 proto dhcp metric 600    ← 무선(metric이 크면 뒤로 밀린다)
  • PC의 주소는 192.168.x.20 같은 사설 주소다. 공유기가 나눠 준다(DHCP).
  • 바깥으로 가는 패킷은 모두 기본 경로인 공유기(192.168.x.1)로 보낸다. 공유기를 기본 게이트웨이라고도 한다.
  • 공유기는 나가는 패킷의 보낸 사람 주소를 자기 공인 주소(예: 203.0.113.7)로 바꿔 내보낸다. 이것을 NAT라 한다. 외부 서버에는 이 공인 주소만 보인다.
  • 그래서 바깥 사람은 PC를 직접 부를 수 없다. 공유기 뒤에 숨어 있기 때문이다. 로컬 서버를 0.0.0.0에 묶어도 인터넷에서는 들어오지 못한다.
  • 같은 사무실 사람들은 공인 주소 하나를 함께 쓴다. 주소마다 세는 요청 한도(10절)를 남이 다 쓸 수 있는 이유다.

라우팅: 여러 정거장을 거쳐 간다

패킷은 목적지까지 라우터라는 중계기를 여러 개 거친다. 각 라우터는 "이 주소로 가려면 다음은 저쪽"만 알고 넘긴다.

tracepath -n -m 8 185.199.109.153    # 처음 8구간만

 1:  192.168.x.1    0.9ms    ← 공유기
 2:  no reply                ← 응답하지 않게 설정된 라우터(정상이다)
 3:  10.x.x.x       2.0ms    ← 통신사 내부망(통신사 안에서도 사설 주소를 쓴다)
 5:  a.b.c.d        3.0ms    ← 통신사 공인망
 …                           ← 실제로는 목적지까지 더 간다

TLS: 진짜 그 서버인지 확인하고 암호화한다

https의 s가 TLS다. TCP 통로가 열린 뒤, HTTP를 보내기 전에 두 가지를 한다.

  1. 신원 확인. 서버가 인증서를 보인다. OS와 브라우저에는 믿을 수 있는 발급 기관 목록이 들어 있다. 클라이언트는 인증서의 서명이 그 목록의 기관 것인지, 이름이 접속한 주소와 맞는지, 기간이 지나지 않았는지 확인한다. 누군가 중간에서 가짜 서버로 가로채면 여기서 걸린다. 주소창의 자물쇠가 이 확인을 통과했다는 표시다.
  2. 암호화. 서로 열쇠를 정한 뒤 그 뒤의 모든 내용을 암호화한다. 같은 와이파이의 다른 사람이나 통신사는 내용을 읽지 못한다. 보이는 것은 어느 주소와 통신하는지까지다.
echo | openssl s_client -connect geonhee-lee.github.io:443 -servername geonhee-lee.github.io 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

subject=CN = *.github.io                       ← "나는 github.io의 서버다"
issuer=C = US, O = Let's Encrypt, CN = YR1     ← 이것을 보증한 발급 기관
notBefore=Sep 30 23:44:46 2026 GMT             ← 90일짜리, 자동으로 갱신된다
notAfter=Dec 29 23:44:45 2026 GMT

CDN: 가까운 사본이 답한다

CDN(콘텐츠 전송망)은 같은 파일의 사본을 전 세계 곳곳의 서버에 두고, 요청한 사람에게 가까운 서버가 답하게 하는 구조다. 응답 헤더를 보면 누가 답했는지 알 수 있다.

curl -sI https://geonhee-lee.github.io/travplan-site/

HTTP/2 200
server: GitHub.com
cache-control: max-age=600              ← 10분 동안 다시 묻지 말고 써라
access-control-allow-origin: *          ← 어느 출처의 페이지든 읽어도 된다
via: 1.1 varnish                        ← 캐시 서버 프로그램을 거쳤다
x-served-by: cache-icn…-ICN             ← 인천(ICN)의 캐시 서버가 답했다
x-cache: HIT                            ← 그 캐시에 이미 사본이 있었다

공개 사이트가 갱신되는 흐름은 페이지가 만들어지는 방식 5절에 있다. push 직후 몇 분은 CDN에 옛 사본이 남아 있을 수 있다.

로컬과 외부를 한 그림으로

[로컬]  curl ──TCP──▶ 127.0.0.1:8765 (PC 안에서 돌아옴) ──▶ http.server ──▶ docs/ 파일

[외부]  curl ──DNS───▶ "geonhee-lee.github.io는 185.199.109.153"
             ──TCP───▶ 공유기 ─(NAT)─▶ 통신사 망 ─▶ … ─▶ 185.199.109.153:443
             ──TLS───▶ 인증서 확인, 암호화 통로
             ─HTTP/2─▶ 가까운 CDN 캐시 ─(사본이 없으면)─▶ GitHub Pages 원본

10API와 인증

API는 사람용 페이지 대신 프로그램이 읽을 데이터(JSON)를 주는 주소다. 같은 HTTP를 쓰고, 누구인지는 요청마다 토큰으로 밝힌다.

요청 결과 한도
curl, 로그인 없이 403, "API rate limit exceeded for 203.0.113.7" 공인 주소 하나당 시간당 60회
gh api, 토큰을 붙여서 200, {"full_name":"Geonhee-LEE/travplan-site","private":false,…} 계정 하나당 시간당 5000회
  • 두 요청은 주소도 메서드도 같다. 다른 것은 요청 헤더 한 줄(Authorization: 토큰)이다. HTTP는 기억하지 않으므로 gh는 요청마다 토큰을 붙인다.
  • 로그인 없는 요청은 어느 공인 주소에서 왔는지로만 센다. 같은 공인 주소를 쓰는 누군가가 60회를 다 쓰면 나도 막힌다.
  • 남은 횟수는 /rate_limit로 본다. 이 주소는 횟수를 깎지 않는다.
  • 토큰은 비밀번호와 같다. 저장소 문서와 공개 사이트에 넣지 않는다. 공개 사본의 위생 검사(페이지가 만들어지는 방식 6절)가 토큰 모양을 찾아 막는다.
curl -s https://api.github.com/rate_limit | python3 -m json.tool | head -12   # 로그인 없는 한도
gh api rate_limit --jq .resources.core                                         # 토큰을 붙인 한도
gh api repos/Geonhee-LEE/travplan-site --jq '{full_name, private, pushed_at}'

11브라우저의 규칙

브라우저는 페이지가 어디서 왔는지(출처)를 보고, 다른 출처의 것을 함부로 섞지 못하게 막는다. Playground를 http 서버로 여는 이유가 이 규칙이다.

출처(origin)

출처는 방식, 주소, 포트의 조합이다. 셋 중 하나만 달라도 다른 출처다.

주소 출처 같은가
http://127.0.0.1:8765/playground/ http://127.0.0.1:8765 기준
http://127.0.0.1:8765/dashboard.html http://127.0.0.1:8765 같다
http://127.0.0.1:8766/playground/ http://127.0.0.1:8766 다르다(포트)
http://localhost:8765/playground/ http://localhost:8765 다르다(주소 글자)
file://로 연 디스크의 playground/index.html 없음(null) 어느 것과도 다르다

브라우저 저장소(localStorage)도 출처마다 따로다. 그래서 8765와 8766에서 연 Playground는 저장한 설정을 서로 보지 못한다.

ES 모듈과 file://

  • Playground는 JS 파일들을 ES 모듈(<script type="module">)로 서로 불러 쓴다. 브라우저는 모듈을 불러올 때 출처 검사(CORS)를 한다.
  • file://로 연 페이지는 출처가 없다. 그래서 Chrome은 같은 폴더의 모듈도 막는다. 개발자 도구에는 blocked by CORS policy가 찍힌다.
  • http://127.0.0.1:8765로 열면 출처가 생긴다. 모듈이 같은 출처에서 오므로 막히지 않는다.

CORS 헤더

다른 출처의 페이지가 데이터를 읽게 해 줄지는 서버가 응답 헤더로 정한다. GitHub Pages가 보내는 access-control-allow-origin: *은 "어느 출처의 페이지든 읽어도 된다"는 뜻이다.

12셸 쪽 용어

서버를 띄우고, 뒤에 두고, 끄는 일은 셸이 한다. 아래는 그때 쓰는 말들이다.

용어 뜻
터미널, 셸 명령을 입력하는 창(터미널)과, 그 명령을 해석해 실행하는 프로그램(셸, 여기서는 bash)
포그라운드, 백그라운드 끝날 때까지 터미널을 붙잡는 실행과, 뒤에서 돌고 터미널은 바로 돌려주는 실행
명령 & 명령을 백그라운드로 돌린다. $!에 그 pid가 남는다
nohup 명령 터미널이 닫혀도 같이 꺼지지 않게 한다. 재부팅은 견디지 못한다
SIGHUP 터미널이 닫힐 때 그 안의 프로그램에 가는 "끝내라" 신호. nohup은 이 신호를 무시하게 한다
Ctrl+C, SIGINT 포그라운드 프로그램을 멈추는 키와 그때 가는 신호
kill <pid> 그 프로세스에 끝내라는 신호(SIGTERM)를 보낸다
pid 프로세스마다 붙는 번호
systemd 부팅할 때 프로그램을 띄우고, 죽으면 다시 살리는 관리자
PATH 셸이 python3 같은 명령을 찾아볼 폴더 목록. 앞에 적힌 폴더부터 찾는다
가상환경(.venv) 이 저장소 전용 파이썬과 패키지를 담은 폴더. source .venv/bin/activate가 PATH 맨 앞에 .venv/bin을 넣는다
set -e 스크립트에서 명령 하나가 실패하면 그 자리에서 멈춘다. open_dashboard.sh가 대시보드 만들기에 실패하면 서버까지 가지 않는 이유다
$? 바로 앞 명령의 종료 코드. 0이면 성공이다

재부팅 뒤에도 서버 띄우기(선택)

systemd 사용자 서비스로 등록하면 로그인할 때 서버가 뜨고, 죽으면 다시 뜬다. 이 서버는 파일을 내주기만 한다. 대시보드를 새로 만드는 일은 여전히 render_dashboard.py가 한다.

mkdir -p "$HOME/.config/systemd/user"
cat > "$HOME/.config/systemd/user/travplan-docs.service" <<'EOF'
[Unit]
Description=travplan docs on 127.0.0.1:8765

[Service]
WorkingDirectory=%h/<저장소 경로>/docs
ExecStart=/usr/bin/python3 -m http.server 8765 --bind 127.0.0.1
Restart=on-failure

[Install]
WantedBy=default.target
EOF
systemctl --user daemon-reload
systemctl --user enable --now travplan-docs     # 지금 띄우고, 다음 로그인부터 저절로 띄운다
systemctl --user status travplan-docs           # 상태 보기. 끄려면 disable --now

%h는 systemd가 홈 폴더로 바꿔 주는 표시다. <저장소 경로>는 홈 아래의 저장소 위치로 바꾼다.

13명령 모음

자주 쓰는 명령을 하는 일별로 모았다. 저장소 루트에서 돌린다.

띄우기와 끄기

source .venv/bin/activate
./scripts/open_dashboard.sh                                        # 대시보드를 만들고 8765로 띄워 연다
PORT=8766 ./scripts/open_dashboard.sh                              # 8765가 차 있을 때
python3 -m http.server 8765 --bind 127.0.0.1 --directory docs      # 대시보드는 그대로 두고 서버만, 앞에서
ss -ltnp | grep :8765                                              # 누가 8765를 쓰는지(pid)
kill <pid>                                                         # 그 서버를 끈다

상태 보기

ss -ltn                                  # listen 중인 포트
nc -zv 127.0.0.1 8765                    # 그 포트에 서버가 있나
uptime -s                                # 마지막 부팅 시각
which python3                            # 어느 파이썬을 집나

HTTP 들여다보기

curl -v http://127.0.0.1:8765/ -o /dev/null                          # 대화 전체
curl -sI http://127.0.0.1:8765/dashboard.html                       # 헤더만
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8765/nope  # 상태 코드만
printf 'GET / HTTP/1.0\r\n\r\n' | nc -q 2 127.0.0.1 8765 | head      # 손으로 쓴 요청

외부 확인

curl -v https://geonhee-lee.github.io/travplan-site/ -o /dev/null    # TLS와 CDN 헤더까지
curl -sI http://geonhee-lee.github.io/travplan-site/                # https로 돌려보내는 301
dig +short geonhee-lee.github.io                                    # DNS 답
ip route show default                                               # 공유기로 가는 기본 경로
tracepath -n -m 8 185.199.109.153                                   # 거쳐 가는 라우터
curl -s https://api.github.com/rate_limit | head -12               # API 남은 횟수
